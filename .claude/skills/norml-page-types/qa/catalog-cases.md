# Catalog acceptance cases

Use these as review scenarios for matching and maintenance. They are expected
decisions from the written contract, not evidence of deployed client behavior.

| Input | Required result |
|---|---|
| About Us lists public people with profiles | about-us/archive + single; logical archive retained even if native Page |
| About Us has no public people | singleton variant; no manufactured people directory/singles |
| Team is already a separate directory | optional team-archive; same person identities, not duplicated records |
| Industry contains service child pages | industries/industry-by-service, both parents, one eligible tuple/route |
| Service-first links to same industry pair | Same member and identity; no duplicated industries/services specification |
| 20 services and 30 areas supplied | 600 candidate pairs only; evaluate each relationship, no automatic approval |
| An area is served remotely | areas-of-service; no invented physical branch/address |
| A real office has visitor details | locations family; coverage model stays separate |
| A question needs a detailed shareable answer | faq archive/topic/single as justified, not a blog article by default |
| Three short questions in a service accordion | Embedded-only FAQ records; no mandatory FAQ singles |
| Product is informational software | Products family; commerce block spec only if it actually fits |
| Classification of cases by industry | Case listing distinct from substantive industry single |
| One Contact page | Singleton; no fake Contact CPT/archive/single pair |
| Requested third-axis intersection conflicts with project rules | Defer/omit; two-axis support grants no authority |
| A new member joins an existing family | Flat sibling file, local/root/quick indexes reconciled |
| New family has no substantive specs | Incomplete; cannot be advertised as usable |
| Collection requires CMS mapping but existing model unknown | Mapping unresolved; no new CPT from path appearance |
| Canonical structure lacks the member’s variant | Explicit structure gap; no guessed required blocks |
| Existing and planned pages are mixed in inventory | Separate observed, approved-planned and proposed states |

## Project-pattern matching cases

| Input | Required result |
|---|---|
| External school lists courses/instructors | providers/single; staff/partner status not inferred |
| Instructor belongs to external school | experts/single; actual affiliation, not About Us staff |
| Directory compares third-party courses | courses family; owned delivery stays in programs |
| Rich subject page lists courses | disciplines/single; logical single and native query separated |
| Focused topic relates to multiple subjects | specialties/single; no forced one-parent tree |
| Named preset overlaps a specialty URL | Preserve observation; require canonical/intent review |
| Shop groups products by their use | solutions/application-single; products remain canonical |
| Sale or new-arrivals label | products/curated-listing; verify selection predicate separately |
| Brand/category/format listing | Brand or compatibility listing; no copied product identities |
| Unpublished concepts with external previews | portfolio/concept-gallery; no delivered-work claims or mandatory singles |
| Empty checkout redirects to cart | commerce/checkout recognized; functional checkout remains unverified |
| Order-bound review shows missing-order state | testimonials/review-collection; no submitted review or public detail inferred |
| Language-prefixed local service | Same service/area identity with a locale representation |
| Sitemap entry returns 404 | Discovery lead only; not a successful page precedent |
| Public calculator with controls | tools/calculator; formula and result accuracy not verified by presence |

## Static package review

1. Frontmatter name matches folder; version matches changelog and generated guides.
2. Every page-types directory has exactly one same-name overview and flat members.
3. Every member appears in index.md and its overview; all relative links resolve.
4. Every family appears in SKILL.md’s quick index and complete index.md.
5. Each member records purpose, role, route/identity/parents, content responsibility,
   relationships, eligibility/omission and structure/implementation handoff.
6. Singletons and embedded-only exceptions do not get meaningless mandatory pairs.
7. Combinations name both parents, one owner and route orientation; no automatic
   generation, duplicate reverse destinations or third-axis authorization.
8. No client content, secrets, local paths, blank scaffolds or generic drawers.
9. Run shared lints; verify adapters twice through supported registration and
   generated human docs at desktop/mobile. Keep screenshots out of skill source.

For a project recommendation additionally reconcile actual entity sources,
native roles, identity, routes and parent navigation with the existing model.
Catalog checks alone cannot establish implemented routes, content, form delivery
or other runtime behavior; consuming build skills own that verification.

## Comparison family acceptance

| Scenario | Expected decision |
|---|---|
| Maintained vendor-versus-vendor section | comparisons archive/single; verify eligible pairs |
| Reverse B-versus-A page | Same identity as A-versus-B, not another URL |
| Existing blog comparison | Reconcile canonical ownership before publication |
| Own free/pro plan table | pricing family, not competitor comparison |
| Visual before/after work | portfolio/comparison-gallery |
| Missing feature on a vendor's homepage | Unknown, not a verified absence |
| Requested 15 pair pages | Fifteen individual eligibility checks, not authority to invent facts |
| Draft content, deployed templates | Private draft records; public listing must exclude them |
| One-to-many roundup | Editorial or separately defined member, not implied pair support |
