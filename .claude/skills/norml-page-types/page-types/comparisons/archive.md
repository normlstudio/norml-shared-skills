# Comparison archive

Family: [Comparisons and alternatives](comparisons.md).
Member ID: `comparisons/archive`. Logical role: `archive`.

## Purpose and fit

Give visitors a coherent entry point to a maintained comparison collection.
Use the existing blog/topic archive if it already fulfills that same purpose.

## Route, identity and parents

- Illustrative route: `/comparison/`; project selects the canonical spelling.
- Identity: the maintained set of comparison records, not all possible pairs.
- Navigation parent: product/resources/global navigation, as approved.
- Native role: dedicated collection archive or curated existing collection hub;
  CMS owner resolves it. URL depth does not imply hierarchical storage.

## Content responsibility

Explain the scope and selection criteria; link only eligible visible records.
Titles, pair identities and summaries come from canonical comparison records.
Unpublished drafts must not leak via listings, search or public API queries.
Classification/filtering is optional and needs useful verified content volume.

## Relationships and navigation

Link comparison singles and relevant owned product/service sources. Preserve
one canonical comparison when older editorial content covers the same intent.

## Eligibility, omission and variants

Choose public, embedded-only, deferred or disabled intentionally. A public empty
hub should explain its state and provide a useful next destination; its index
policy is a project decision. Never publish empty cards for promised articles.

## Structure and implementation handoff

Comparison-specific structure is a gap. Existing blog archive elements can
inform an explicitly recorded project layout without importing unrelated topic
or author controls. Hand state, route, query role and record source to
sitemap planning and the CMS/build owners.
