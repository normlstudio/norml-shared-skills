# Comparisons and alternatives

Family ID: `comparisons`. A maintained collection of evidence-backed evaluations.

## Purpose and fit

Help visitors choose between a product/service and a real alternative using
explicit criteria. Select when comparisons form a maintained decision resource
with its own browse journey. An occasional opinion/roundup can remain in blog.
Pricing compares the organization's own plans; portfolio comparison galleries
show visual before/after work. Neither owns competitor evaluation records.

## Canonical entity and model

One comparison relationship between identified offerings for a defined decision.
Store entity facts once and reference them; the comparison owns contextual
tradeoffs, evidence and review date. The same pair in reverse order is not a
second record. A distinct audience alone does not authorize another near-copy.

An existing editorial collection may suffice; an independently managed section
may warrant a dedicated collection. `WordPress architecture review` resolves the actual
CMS model. A family name never requires a new CPT by itself.

## Included members

| Member ID | File | Logical role | Purpose / when enabled |
|---|---|---|---|
| `archive` | [archive.md](archive.md) | archive | Browse approved comparison destinations. |
| `single` | [single.md](single.md) | intersection | Evaluate one eligible pair for a documented visitor decision. |

Evaluate hub and single availability together. Short pair notes can stay
embedded; an archive can be deferred while its records are drafts. Never imply
that an approved architecture means published content or tested feature parity.

## Relationships, depth and combinations

Archive → comparison single; each single references both offering identities
and relevant canonical product/service destinations where they exist. External
competitors need not receive invented local product pages. Navigation parent,
URL parent and CMS hierarchy are independent. Choose one route orientation.
No automatic all-pairs multiplication, competitor taxonomy or extra category
archive. Each added branch needs actual visitor purpose and its own contract.

## Eligibility and content truth

Apply the architecture per-pair gate. Each pair needs current attributable
sources, distinct decision criteria, honest strengths/limitations for both sides,
a review owner/date and explicit unknowns. A missing source is not evidence
that a feature is absent. Distinguish shipped, beta, planned and unavailable
capabilities. Date volatile pricing and plan limits; never invent test results,
ratings, endorsements, affiliation or universal superiority.

Before publishing, reconcile an existing blog comparison for the same intent.
Record one canonical destination; migration/redirects need an explicit plan.
Draft status and editorial approval remain separate from implementation.

## Handoff and provenance

Record family/member, pair identity, criteria, parents, route, state, evidence,
owner/review date and archive/single disposition in the project architecture.
No dedicated comparison spec exists in norml-page-structures at this revision.
Its blog archive/article elements may be adapted only through an explicit
project contract; they are not a complete comparison specification.

Authored reusable pattern from Norml Studio's Oct 12, 2026 request for a separate
